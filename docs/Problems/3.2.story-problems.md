### Issue #1: Statistics Overcounting ✅ FIXED

**ID:** STATS-001
**Severity:** MEDIUM
**Category:** Observability/Monitoring
**Status:** ✅ **RESOLVED** (2025-10-24)

**Problem:**
The `categories_created` and `subcategories_created` counters increment for EVERY skill processed, not for unique categories/subcategories. This results in grossly inflated statistics.

**Location:**
- `backend/app/services/skill_graph_service.py:161`
- `backend/app/services/skill_graph_service.py:170`

**Code Snippet:**
```python
# Current (INCORRECT):
if skill_row.get("CATEGORY"):
    await self._create_category_node(
        tx,
        skill_row["CATEGORY"],
        skill_row.get("CATEGORY_NAME", "")
    )
    batch_stats["categories_created"] += 1  # ❌ Increments for every skill
```

**Example Impact:**
- Processing 1000 skills that all share category "CAT001"
- **Expected:** `categories_created = 1`
- **Actual:** `categories_created = 1000`
- Makes monitoring and debugging extremely difficult

**Root Cause:**
Counter increments without checking if the category/subcategory was already processed in this batch.

**Suggested Fix:**
```python
# Track unique IDs before incrementing counters
unique_categories = set()
unique_subcategories = set()

# In the batch processing loop:
if skill_row.get("CATEGORY") and skill_row["CATEGORY"] not in unique_categories:
    await self._create_category_node(
        tx,
        skill_row["CATEGORY"],
        skill_row.get("CATEGORY_NAME", "")
    )
    unique_categories.add(skill_row["CATEGORY"])
    batch_stats["categories_created"] += 1  # ✅ Only increments for unique IDs
```

**Test Coverage:**
⚠️ Current tests don't validate statistics accuracy (they only check that counters exist and are positive)

**Priority:** HIGH

**✅ Implemented Fix:**
```python
# Added in create_skill_graph() method (lines 77-79):
unique_categories = set()
unique_subcategories = set()

# Modified in _process_skills_batch() to track unique IDs (lines 170-186):
if skill_row.get("CATEGORY"):
    await self._create_category_node(
        tx,
        skill_row["CATEGORY"],
        skill_row.get("CATEGORY_NAME", "")
    )
    unique_categories.add(skill_row["CATEGORY"])  # Track unique ID

# Update stats with unique counts (lines 101-103):
stats["categories_created"] = len(unique_categories)
stats["subcategories_created"] = len(unique_subcategories)
```

**Files Modified:**
- `backend/app/services/skill_graph_service.py` (lines 77-79, 92-103, 127-135, 170-186)

### Issue #4: Missing Input Validation ✅ FIXED

**ID:** VALIDATION-001
**Severity:** MEDIUM
**Category:** Security/Reliability
**Status:** ✅ **RESOLVED** (2025-10-24)

**Problem:**
Direct dictionary access without validation can cause `KeyError` with malformed CSV data. Required fields like `ID` and `NAME` are accessed without checking if they exist.

**Location:**
- `backend/app/services/skill_graph_service.py:295` (and other dict accesses throughout)
- Lines: 295, 296, 401, 402, etc.

**Code Snippet:**
```python
# Current (UNSAFE):
await tx.run(
    query,
    id=skill_row["ID"],        # ❌ KeyError if missing
    name=skill_row["NAME"],    # ❌ KeyError if missing
    # ...
)
```

**Example Impact:**
```python
# Malformed CSV row:
{"DESCRIPTION": "Python language", "CATEGORY": "PROG"}
# Missing: ID, NAME

# Result: KeyError: 'ID' - crashes batch processing
```

**Root Cause:**
Assumes CSV data is always well-formed. No defensive validation at entry point.

**Suggested Fix (Option 1 - Entry Point Validation):**
```python
async def create_skill_graph(
    self,
    skills_data: List[dict],
    job_id: str
) -> Dict[str, Any]:
    """Create complete skills taxonomy graph from CSV data."""

    # Validate required fields
    required_fields = ["ID", "NAME"]
    for idx, skill in enumerate(skills_data):
        missing = [f for f in required_fields if f not in skill]
        if missing:
            raise ValueError(
                f"Row {idx}: Missing required fields {missing}. "
                f"Available fields: {list(skill.keys())}"
            )

    # Continue with processing...
```

**Suggested Fix (Option 2 - Use .get() with defaults):**
```python
# More defensive:
id=skill_row.get("ID", f"missing-{idx}"),  # ⚠️ Still not ideal
name=skill_row.get("NAME", "Unknown"),     # ⚠️ Creates bad data
```

**Recommendation:** Use **Option 1** (fail fast with clear error message)

**Test Coverage:**
❌ No tests for malformed input handling

**Priority:** HIGH

**✅ Implemented Fix:**
```python
# Added validation method (lines 35-61):
def _validate_required_fields(self, skills_data: List[dict]) -> None:
    """
    Validate that all required CSV fields are present.

    Raises:
        ValueError: If required fields are missing or empty
    """
    required_fields = ["ID", "NAME"]

    for idx, skill_row in enumerate(skills_data):
        missing_fields = [field for field in required_fields if field not in skill_row]
        if missing_fields:
            raise ValueError(
                f"Row {idx + 2}: Missing required fields {missing_fields}. "
                f"Required fields are: {required_fields}"
            )

        # Check that required fields are not empty
        for field in required_fields:
            if not skill_row.get(field) or str(skill_row.get(field)).strip() == "":
                raise ValueError(
                    f"Row {idx + 2}: Field '{field}' is empty or whitespace. "
                    f"All required fields must have non-empty values."
                )

# Called at entry point (line 64):
self._validate_required_fields(skills_data)
```

**Files Modified:**
- `backend/app/services/skill_graph_service.py` (lines 35-64)

### Issue #5: No Retry Logic for Transient Failures ⏳ DEFERRED

**ID:** RETRY-001
**Severity:** LOW
**Category:** Reliability
**Status:** ⏳ **DEFERRED** (Acceptable for MVP, planned for production)

**Problem:**
Transient database connection failures (network blips, brief Neo4j unavailability) will permanently abort the batch with no retry attempt.

**Location:**
- `backend/app/services/skill_graph_service.py:147-191`

**Example Impact:**
- Temporary network issue during batch 5 of 10
- Entire batch fails permanently
- Manual re-run required (though MERGE makes this safe)

**Root Cause:**
No retry mechanism for transient errors.

**Suggested Fix:**
```python
from tenacity import (
    retry,
    stop_after_attempt,
    wait_exponential,
    retry_if_exception_type
)
from neo4j.exceptions import ServiceUnavailable, SessionExpired

@retry(
    retry=retry_if_exception_type((ServiceUnavailable, SessionExpired)),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10)
)
async def _process_skills_batch_with_retry(...):
    # Existing batch processing logic
```

**When to Implement:**
- ✅ MVP: Acceptable without retry (MERGE ensures idempotency)
- ⚠️ Production: Should add retry for better reliability

**Test Coverage:**
❌ No tests for transient failure scenarios

**Priority:** MEDIUM (for production), LOW (for MVP)
